## 1. DATA PRIVACY & DATA MINIMIZATION (AADHAAR & IDENTITY)

### 1.1 Aadhaar Data Minimization Compliance
Under Indian UIDAI regulations and Supreme Court precedents (*K.S. Puttaswamy* & Aadhaar Act regulations), non-banking platforms are prohibited from collecting or storing unmasked 12-digit Aadhaar numbers or biometric credentials without explicit UIDAI license.

**Implementation Enforcement:**
- In `apps/api/src/common/encryption/encryption.service.ts`:
  ```typescript
  if (/^[2-9]\d{11}$/.test(clean)) {
    throw new BadRequestException('Aadhaar number storage prohibited. Use alternate KYC.');
  }
  ```
- Every attempt to submit or encrypt a 12-digit Aadhaar sequence fails immediately with an HTTP 400 rejection.
- Partner and merchant onboarding forms collect official regulatory alternatives: Driving License, PAN, Vehicle Registration Certificate (RC), and FSSAI license numbers.

### 1.2 Sensitive Field Masking
All API endpoints returning merchant or partner dossiers enforce strict field-level masking before response serialization:
- **Permanent Account Number (PAN):** Formatted as `ABCDE****F` (first 5 characters, 4 asterisks, last 1 character).
- **Bank Account Numbers:** Formatted as `******1234` (all digits masked except last 4).
- **UPI Handles:** Formatted as `j***@okaxis` (first character, 3 asterisks, `@bank_vpa`).

## 2. CRYPTOGRAPHIC STORAGE ARCHITECTURE

### 2.1 AES-256-GCM Authenticated Encryption
Sensitive PII columns in PostgreSQL (such as payout details) are protected using AES-256 in Galois/Counter Mode (GCM):
- **Key Derivation:** Master 256-bit key sourced from `ENCRYPTION_MASTER_KEY` environment variable.
- **Nonce/IV Generation:** Cryptographically secure 96-bit (12-byte) random initialization vector generated per encryption operation using `crypto.randomBytes(12)`.
- **Authentication Tag:** 128-bit (16-byte) authentication tag generated by GCM to guarantee ciphertext integrity and authenticity.
- **Envelope Format:** Ciphertext is serialized as `v1:<base64(iv + ciphertext + authTag)>`. Modifying a single bit of ciphertext results in an authenticated decryption error.

### 2.2 Blind Indexing via HMAC-SHA256
To allow duplicate detection and database indexing of encrypted fields (e.g. checking whether a bank account number has already been registered) without decrypting data, a separate cryptographic mechanism is used:
- **Blind Index Key:** Sourced from `FIELD_HMAC_KEY` (distinct from `ENCRYPTION_MASTER_KEY`).
- **Hash Computation:** `crypto.createHmac('sha256', FIELD_HMAC_KEY).update(normalizedValue).digest('hex')`.
- This ensures deterministic querying in PostgreSQL (`WHERE bank_account_hmac = $1`) while preventing attackers who obtain the database dump from performing frequency or equality attacks without the distinct HMAC key.

## 3. PRIVATE DOCUMENT STORAGE & FILESYSTEM PROTECTION

### 3.1 Canonical Path Containment & Traversal Defense
Private document storage is located outside web-accessible roots at `LOCAL_STORAGE_ROOT` (defaults to `<project_root>/allgo_private_storage`).
- **Traversal Prevention:**
  ```typescript
  const resolved = path.resolve(this.storageRoot, relativePath);
  const rel = path.relative(this.storageRoot, resolved);
  if (rel.startsWith('..') || path.isAbsolute(rel)) {
    throw new ForbiddenException('Path traversal attempt rejected');
  }
  ```
- Any payload containing `..`, null bytes, or absolute path strings is rejected prior to filesystem interaction.

### 3.2 Symlink & Junction Attack Prevention
Attackers attempting to create symbolic links pointing to sensitive system files (e.g., `/etc/passwd` or `C:\Windows\System32`) are blocked using explicit `fs.lstatSync` inspections. If `lstat.isSymbolicLink()` returns true, the file access operation is terminated immediately.

### 3.3 Deep Structural MIME Inspection
File extensions and client-supplied `Content-Type` headers are considered untrusted. The storage service performs multi-layered inspection:
1. **Magic Number Verification:**
   - PDF: Must begin with `%PDF` (`0x25 0x50 0x44 0x46`).
   - PNG: Must begin with `\x89PNG\r\n\x1a\n` (`0x89 0x50 0x4E 0x47 0x0D 0x0A 0x1A 0x0A`).
   - JPEG: Must begin with `\xFF\xD8\xFF`.
2. **Structural EOF / EOI Marker Inspection:**
   - PDF files must contain the `%%EOF` end-of-file trailer within their final 1024 bytes.
   - PNG files must contain the `IEND` chunk marker within their final 12 bytes.
   - JPEG files must terminate with the `\xFF\xD9` end-of-image marker.
3. **MIME Whitelist:** Strictly restricted to `application/pdf`, `image/jpeg`, and `image/png`. Executables, scripts, HTML, and SVG files are rejected.

### 3.4 Anti-Malware Integration (ClamAV)
The storage subsystem includes a dedicated TCP socket client connecting to ClamAV (`127.0.0.1:3310`):
- Transmits uploaded bytes using ClamAV's `zINSTREAM` protocol.
- If ClamAV detects a signature match (`FOUND`), the file is immediately deleted from disk, the upload ticket is marked `FAILED`, and an alert is logged.
- In production mode (`CLAMAV_STRICT_MODE=true`), if ClamAV daemon is unreachable, the system fails closed and rejects all file uploads.

## 4. INSECURE DIRECT OBJECT REFERENCE (IDOR) & AUTHORIZATION DEFENSES

### 4.1 Ticket Ownership Binding
Upload tickets are pre-allocated via `POST /v1/storage/upload-ticket`. The ticket record in PostgreSQL explicitly binds `user_id` to the session owner.
- When `PUT /v1/storage/upload/:ticketId` is executed, the session user ID must match `ticket.user_id`.
- When `POST /v1/partner/documents` or `POST /v1/merchants/documents` is executed, the submitting entity's owner must match `ticket.user_id`.
- Verified in `tests/backend/phase2-integration-security.spec.ts`: An attempt by User B to submit or link a ticket created by User A throws an immediate `ForbiddenException: Document upload ticket ownership mismatch`.

### 4.2 Authenticated Document Streaming
Documents are never accessible via public URLs or static web directories:
- Retrieval requires `GET /v1/storage/documents/:ticketId`.
- Access is restricted to:
  1. The document owner (the partner or merchant user who uploaded it).
  2. Authenticated administrators possessing `role: 'ADMIN'` and `role: 'SUPER_ADMIN'`.
- All requests by unauthorized third parties receive `HTTP 403 Forbidden`.

## 5. IMMUTABLE AUDIT TRAIL & REASON ENFORCEMENT

### 5.1 Database-Level Immutability Trigger
To satisfy regulatory requirements and prevent insider tampering:
- In `database/migrations/003_phase2_kyc_and_onboarding.sql`, a PostgreSQL trigger `trg_audit_logs_immutable` is attached to `audit_logs`:
  ```sql
  CREATE OR REPLACE FUNCTION fn_audit_logs_immutable()
  RETURNS TRIGGER AS $$
  BEGIN
    RAISE EXCEPTION 'audit_logs entries are strictly immutable and cannot be updated or deleted';
  END;
  $$ LANGUAGE plpgsql;

  CREATE TRIGGER trg_audit_logs_immutable
  BEFORE UPDATE OR DELETE ON audit_logs
  FOR EACH ROW EXECUTE FUNCTION fn_audit_logs_immutable();
  ```
- This ensures that even privileged database connections cannot alter or delete historical KYC review records.

### 5.2 Mandatory Audit Reasons
All administrative actions in `apps/api/src/partner/admin-partner.controller.ts` and `apps/api/src/merchant/admin-merchant.controller.ts` enforce non-empty reason strings. Any approval, rejection, or suspension request without an explicit reason is rejected with `HTTP 400 Bad Request`.
